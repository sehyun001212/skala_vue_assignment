# Weather App 프로젝트

Vue 3 Composition API를 기반으로 만든 실시간 날씨 대시보드입니다. 도시 검색, 즐겨찾기, 온도 단위 변환, 도시별 상세 페이지, 도시별 온도 차트 등 기능을 추가했으며 OpenWeatherMap과 Wikipedia API를 연동해 실제 데이터를 사용했습니다.

## 기술 스택

- Vue 3 (Composition API, `<script setup>`)
- Vue Router
- Pinia
- Axios
- Element Plus
- Chart.js / vue-chartjs

---

## 1. 컴포넌트 설계

처음에는 `WeatherMockup.vue` 하나에 검색창과 날씨 카드 등 대부분의 UI가 들어가 있었습니다. 기능을 추가하다 보니 가독성이 좋지 않아 역할과 기능에 따라 컴포넌트를 나누었습니다.

- `BaseDashboardCard.vue`: 검색창과 카드 목록을 감싸는 흰색 박스 영역입니다. `<slot>`을 사용해 내부 콘텐츠는 사용하는 쪽에서 자유롭게 넣을 수 있도록 만들었습니다.
- `SearchBar.vue`, `WeatherCard.vue`, `SortControl.vue`: 각각 필요한 값을 props로 전달받고, 클릭이나 입력 이벤트는 emit을 통해 부모에게 전달하도록 구성했습니다.

실제 데이터 변경은 부모인 `WeatherHomeView.vue`에서 처리하고 자식 컴포넌트는 화면을 보여주거나 이벤트를 전달하는 역할을 하게 했습니다.

### 초기 트러블슈팅 - 오타와 실수

컴포넌트를 나누는 과정에서는 생각보다 사소한 오타 때문에 화면이 렌더링되지 않는 경우가 많았습니다.

- 'p'태그를 대문자 'P'태그로 작성해 오류가 난 문제
- 닫는 태그에서 '/'를 빠뜨려 이후 구조까지 함께 꼬인 문제
- {{ boxWidth }} 뒤에 `}}'를 하나 더 써서 문법이 깨진 문제
- :key를 `: key="key"`처럼 작성해 v-bind 축약 문법으로 인식되지 않은 문제 등등..

처음에는 화면이 왜 나오지 않는지 답답했지만 콘솔과 에디터 Problems 탭을 확인하면서 하나씩 수정했습니다. 직접 경험하면서 에러 메시지를 확인하고 해결해나가는 경험을 할 수 있었습니다.

## 2. 반응형 상태 관리

Composition API의 `ref`, `computed`, `watch`, `watchEffect`를 사용해 검색, 정렬, 즐겨찾기 등의 상태를 관리했습니다.

검색어는 `searchQuery`에 저장하고 `filteredWeatherList`를 computed로 만들어 검색어가 없으면 전체 도시를, 검색어가 있으면 조건에 맞는 도시만 보여주도록 했습니다.

`watch`는 상태바 문구의 변경을 확인하는 데 사용했고, `watchEffect`를 이용해 검색어가 변경될 때마다 반응형 상태가 어떻게 동작하는지도 확인해볼 수 있었습니다.

### 즐겨찾기 + 정렬 로직 시행착오

처음에는 즐겨찾기한 도시를 위쪽에 따로 보여주려고 화면을 위부터 즐겨찾기 영역 / 구분선 / 전체 도시 영역으로 나눠 보여주려 했습니다. 그런데 같은 `WeatherCard` 마크업을 두 번 작성해야 한다는 것을 깨닫고 저한테는 좀 복잡한 과정이라 느껴 정렬 순서만 바꾸는 방법으로 방향을 바꿨습니다. 즐겨찾기 여부를 `1`, `0`처럼 비교해 즐겨찾기된 도시가 맨 앞으로 나오도록 했습니다.

이 과정에서 정렬 관련 문제도 있었습니다. 처음에는 즐겨찾기 정렬을 담당하는 `sortedByFavorite`과 온도 정렬을 담당하는 `sortedWeatherList`를 각각 별도의 computed로 만들었습니다. 그런데 온도 정렬을 다시 적용하면서 앞에서 만든 즐겨찾기 순서가 덮어써지는 문제가 생겼습니다.

결국 다음을 하나의 `.sort()` 안에서 처리하도록 했습니다.

1. 즐겨찾기 여부가 다르면 즐겨찾기를 먼저 정렬
2. 즐겨찾기 여부가 같으면 선택한 온도 기준으로 정렬

이렇게 우선순위를 정해서 해결할 수 있었습니다.

## 3. Vue Router

처음에는 하나의 컴포넌트 안에 여러 화면을 넣어두었지만 기능이 늘어나면서 페이지 단위로 분리했습니다.

- `WeatherHomeView.vue`: 메인 화면
- `WeatherAboutView.vue`: 프로젝트 소개
- `WeatherDetailView.vue`: 도시 상세 페이지
- `FavoriteListView.vue`: 즐겨찾기 목록
- `NotFoundView.vue`: 404 페이지

각 페이지에는 `() => import(...)` 형태의 Lazy Loading을 적용했습니다. 각 페이지 코드를 처음부터 다 불러오지 않고 실제로 그 경로에 접속하는 시점에만 불러오도록 해서 앱 초기 로딩 시 필요 없는 코드까지 다운로드하지 않아도 되어 초기 로딩 속도를 개선할 수 있습니다.

## 4. Pinia

여러 페이지에서 공통으로 사용하는 상태는 Pinia 스토어로 분리했습니다.

- `favoriteStore.js`: 즐겨찾기한 도시의 id 배열을 state로 관리하고 도시를 추가하거나 제거하는 toggle action을 만들었습니다.
- `configStore.js`: 온도 단위인 `unit`을 state로 관리하고, 현재 단위에 맞는 기호를 반환하는 `unitSymbol` getter와 ℃/℉ 단위를 전환하는 `toggleUnit` action을 만들었습니다.

날씨 데이터 자체도 Pinia에 넣어 여러 화면에서 공유할지 고민했습니다. 프로젝트 규모를 생각해 각 화면이 필요한 데이터를 직접 호출하는 단순한 구조를 유지하기로 결정했습니다.

## 5. Axios & 외부 API 연동

프로젝트를 진행하면서 가장 많은 시행착오가 있었던 부분입니다.

### 실시간 날씨 데이터

OpenWeatherMap의 Current Weather API를 이용해 서울, 부산, 제주, 춘천 총 12개 도시의 실시간 날씨를 가져왔습니다.

API 키를 처음 발급받았을 때 계속 `401 Unauthorized` 오류가 발생했습니다. 코드 문제라고 생각해 여러 부분을 확인했는데 결국 AI에게 물어보니 새로 발급된 API 키가 실제로 활성화되기까지 시간이 걸릴 수 있다는 것을 알게 됐습니다. 일정 시간이 지난 뒤 다시 요청하니 데이터를 받을 수 있었습니다.

처음 도시 목록에는 제 사심을 담은 지역 영월도 포함되어 있었지만 API에서 찾지 못하는 도시라 화면에 뜨지 않아 춘천으로 교체했습니다.

### 미세먼지 데이터 확장

OpenWeatherMap의 Air Pollution API도 추가했습니다.

Current Weather API에서 받은 위도와 경도를 그대로 사용해 Air Pollution API를 한 번 더 호출하고 응답으로 받은 PM10 값을 화면에 표시했습니다.

이미 받아온 좌표를 다음 API 요청에 재사용하면서 API 간 데이터를 연결하는 방식도 경험해볼 수 있었습니다.

### 로딩 관련 버그

`localhost:5173`을 처음 실행하면 API 응답을 기다리는 짧은 시간 동안 화면에 `"검색 결과가 일치하는 도시가 없습니다"`라는 문구가 표시되는 문제가 있었습니다.

데이터 배열이 비어 있는 상태를 단순히 `"검색 결과 없음"`으로만 처리했기 때문이었습니다. 알고 보니

- API 데이터를 불러오고 있는 중
- 로딩이 끝났지만 검색 결과가 없는 경우

두 상황을 구분해야 했습니다.

그래서 `isLoading` 상태를 추가해 로딩 중에는 스피너를 보여주고, 로딩이 끝난 이후에만 검색 결과가 없다는 메시지가 나타나도록 수정했습니다.

### Mock 데이터가 남아 생긴 문제

Router를 적용한 뒤 상세 페이지와 즐겨찾기 페이지에서 문제가 발생했습니다.

기존 Mock 데이터에서는 `city_01`과 같은 id를 사용하고 있었는데 실제 API 연동 이후에는 `Seoul`과 같은 도시 id를 사용하고 있었습니다. 상세 페이지에서는 `"해당 도시 정보를 찾을 수 없습니다"`가 나오고, 즐겨찾기 페이지에서는 목록이 비어 보였습니다.

두 페이지 모두 실제 API 데이터를 기준으로 동작하도록 수정하면서 해결했습니다.
이 과정에서 데이터 구조나 id 규칙을 변경할 때는 해당 데이터를 사용하는 다른 컴포넌트도 함께 확인해야 한다는 점을 배웠습니다.

### 도시 소개 - Wikipedia API

처음에는 Wikipedia의 "오늘의 역사" 기능을 넣어보려 했습니다. 하지만 실제 요청을 보내보니 한국어 위키백과에서는 해당 기능을 지원하지 않았고 저는 영어로 기능을 억지로 유지하기보다는 Wikipedia 페이지 요약 API를 사용하는 방향으로 변경했습니다.

도시 상세 페이지에 해당 도시의 간단한 소개를 보여주도록 했고 OpenWeatherMap에서 사용하는 영문 도시명과 Wikipedia의 한글 문서명을 연결하기 위해 별도의 도시명 매핑 객체를 만들어야 했습니다. 예를 들어 영문 id를 실제 한글 행정구역명으로 변환한 뒤 Wikipedia에 요청하도록 해 검색 정확도를 높였습니다.

### API 키를 `.env`에 넣는 기준

OpenWeatherMap의 API 키를 `.env`에 저장했습니다. 또한 `.gitignore`에 `.env`를 추가해 Git 저장소에 키가 올라가지 않도록 했습니다.

반면 Wikipedia API는 별도의 인증키가 필요하지 않은 공개 API라 URL 자체를 코드에 작성했습니다.

- 처음에는 외부 API와 관련된 값은 전부 `.env`에 넣어야 하는 줄 알았는데 외부에 노출되면 안 되는 인증 정보가 있는지를 기준으로 구분해야는 것을 알게 됐습니다.

## 6. UI 라이브러리 - Element Plus

수업에서 배운 Element Plus도 프로젝트에 적용했습니다.

`main.js`에서 Element Plus를 전역 등록한 뒤 다음 컴포넌트와 기능을 사용했습니다.

- `<el-input>`: 검색창
- `<el-card>`: 날씨 카드
- `<el-tag>`: 온도 상태 표시
- `<el-button>`: 각종 버튼
- `v-loading`: API 로딩 표시
- `ElMessage`: 즐겨찾기 추가/삭제 알림

이 과정에서 온도 단위 전환 버튼의 UX도 한 번 수정했습니다. 섭씨로 표시되고 있는데도 '섭씨 변경하기'로 버튼이 표시되어 현재(섭씨)가 아니라 버튼을 눌렀을 때 변경될 단위(화씨)가 표시되도록 반대로 수정했습니다.

## 7. 추가 기능

### 온도 비교 차트

Chart.js와 vue-chartjs를 설치하고 도시별 현재 온도를 비교할 수 있는 막대그래프를 추가했습니다.

차트 데이터를 별도로 고정하지 않고 화면에 표시되는 도시 목록과 연결해 검색어나 정렬 조건이 변경되면 차트도 함께 변경되게 했습니다.

막대 색상은 최저 온도와 최고 온도를 기준으로 하늘색에서 빨간색까지 변하도록 AI의 도움을 받아 구현했습니다.

### 폰트 및 스타일

전체 폰트는 Pretendard로 변경했습니다.

카드 디자인, 전체 레이아웃의 폭과 정렬, 색상 조합 등 CSS 작업은 AI의 도움을 받으면서 수정했고, 실제 화면에 적용해 보면서 필요한 부분은 직접 값을 조정했습니다.

## 8. 코드 품질 관리

### ESLint

마지막으로 `npm run lint`를 실행해 코드에 문제가 없는지 확인했습니다.

이 과정에서 `catch (error)`로 받아온 `error` 변수를 실제로 사용하지 않아 오류가 발생했습니다. 해당 에러를 확인할 수 있도록 `console.log`를 추가하면서 해결했습니다.

또한 `eslint.config.js`에 다음과 같은 커스텀 규칙을 추가했습니다.

- 'eqeqeq': ['error', 'always']
- 'no-console': 'off',

### Prettier

`.prettierrc.json`은 프로젝트 생성 당시 기본으로 설정된 값을 그대로 사용했습니다.

```json
{
  "semi": false,
  "singleQuote": true,
  "printWidth": 100
}
```

`printWidth`는 정해진 정답이 있는 값이라기보다 한 줄의 최대 길이에 대한 스타일 설정에 가깝다고 판단해 기존의 100을 유지했습니다.
`tabWidth` 역시 Prettier 기본값이 이미 2이기 때문에 굳이 추가하지 않았습니다.

- ESLint와 Prettier는 프로젝트 마지막 단계에서 적용했는데, 하다 보니 교수님께서 말씁하신 것처럼 이런 설정은 원래 프로젝트를 시작할 때 미리 정해두고 가는 게 맞다는 걸 느꼈습니다. 혼자 작업할 때는 크게 영향이 없을지 몰라도 여러 명이 같이 작업하는 실제 프로젝트라면 각자 코드 스타일이 달라서 파일마다 들여쓰기나 따옴표가 제각각이 될 수 있을 것 같았습니다. ESLint와 Prettier를 처음부터 켜두면 이런 차이를 규칙으로 미리 맞춰둘 수 있어서 나중에 코드를 합칠 때 불필요한 충돌이나 리뷰 시간을 줄여줄 것 같다는 생각이 들었습니다.

OpenWeatherMap API 키는 `.env` 파일에 'VITE\_' 접두사를 붙여 저장했습니다.

## 9. 동료 피드백 반영

Git에 push한 뒤 Vercel로 배포하고 동료에게 공유해 사용 후 피드백을 받았습니다.

1. 로딩 스피너가 날씨 카드에만 적용되고 아래 온도 비교 차트 불러올 때는 없음
2. 로딩 스피너만 있는 것보다 지금 무엇을 불러오는 중인지 문구를 같이 보여주면 더 좋을 것 같음

의 피드백을 주었습니다. 동료의 의견을 반영해 온도 비교 차트에도 로딩 스피너를 추가하고 날씨 카드 목록과 비교 차트 두 곳 모두에 로딩 문구를 추가했습니다.
기존에 날씨 카드에만 적용되어 있던 `v-loading="isLoading"`을 차트를 감싸는 `<div>`에도 동일하게 적용해 두 영역이 같은 로딩 상태를 공유하도록 했고 Element Plus의 `element-loading-text` 속성으로 각 영역에 맞는 안내 문구를 추가했습니다.

- 이 과정에서 실수도 있었습니다. 처음에는 `v-loading`이 적용된 `<div>`를 실수로 두 번 겹쳐서 감싸는 바람에 로딩 오버레이가 이중으로 겹쳐 배경과 크기가 이상하게 보였고, 이를 정리하는 과정에서 이번에는 전체를 감싸는 태그의 닫는 부분을 실수로 같이 지워버려서 "Element is missing end tag" 에러가 발생하기도 했습니다. 태그를 다시 하나씩 맞춰가며 최종적으로 정리했습니다.
